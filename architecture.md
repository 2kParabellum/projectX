# Архитектура

Документ описывает структуру проекта, канонические данные, границы модулей и
правила зависимостей. Цель проекта — в `idea.md`.

Имя пакета: **`arbx`**. Язык: Python 3.13.

---

## 1. Конвейер

Система — это линейный конвейер из пяти стадий. Каждая стадия принимает и
отдаёт данные в канонических типах из `arbx/models.py` и не знает ничего о
внутренностях соседних стадий.

```
  [1] SOURCES          [2] NORMALIZE        [3] MATCHING
  per-site adapters -> canonical quotes -> cross-source linking
  Polymarket                                       |
  Fonbet                                           v
  BetBoom                                  [4] ARBITRAGE
  ...                                      detect + size + filter
                                                   |
                                                   v
                                           [5] NOTIFY
                                           Telegram

  всё это запускает [0] ORCHESTRATOR, всё это пишет в [S] STORAGE
```

### Стадия 1 — Sources (сбор)

Один адаптер на площадку. Адаптер знает только про свой сайт: как туда
достучаться, как разложить ответ. Он обязан:

- вернуть **сырой** ответ как есть (`RawSnapshot`) — он сохраняется на диск;
- вернуть список канонических котировок (`Quote`) + событий (`SourceEvent`).

Сырой снимок обязателен: он позволяет переигрывать стадии 2–4 офлайн без
похода в сеть. Это главный инструмент отладки и разработки в ноутбуке.

### Стадия 2 — Normalize (приведение к общему виду)

Чистка строк, перевод/транслитерация названий команд, канонизация типа рынка
и исхода, перевод цены в десятичный коэффициент. Работает с текстом и
числами, в сеть не ходит.

### Стадия 3 — Matching (сопоставление)

Самая сложная часть. Связывает события разных источников в одно логическое
событие (`MatchedEvent`). Работает в три шага:

1. **Blocking** — грубое сужение кандидатов: тот же вид спорта + время начала
   в пределах окна (± несколько часов). Без этого шага сравнение квадратичное.
2. **Scoring** — для каждой пары кандидатов считается уверенность: сначала
   прямое попадание по словарю алиасов, затем нечёткое сравнение
   (`rapidfuzz`) по обоим участникам, затем близость времени начала.
3. **Decision** — выше верхнего порога → автоматическая связка; между
   порогами → в очередь ручной проверки; ниже нижнего → отбрасывается.

Подтверждённые вручную связки пишутся в словарь алиасов и в следующий раз
срабатывают уже на шаге 1. Словарь — это актив, который накапливается.

### Стадия 4 — Arbitrage (расчёт)

Для каждого сопоставленного рынка собирается **полный взаимоисключающий набор
исходов**, по каждому исходу берётся лучший коэффициент среди всех источников,
считается `sum(1/d)`.

- `sum < 1` → вилка, маржа `1 - sum`;
- далее применяется модель издержек (комиссии, проскальзывание по стакану
  Polymarket, лимиты) и фильтры (минимальный профит, свежесть, глубина).

Если набор исходов неполный (например, у букмекера 1X2, а на Polymarket только
«победит ли X» без ничьей) — **ситуация отбрасывается, а не считается**. Это
жёсткое правило: лучше пропустить вилку, чем выдать ложную.

### Стадия 5 — Notify (уведомление)

Форматирование и отправка. Дедупликация: одна и та же вилка не шлётся
повторно, пока её параметры существенно не изменились.

## 3. Канонические данные (`arbx/models.py`)

Это контракт между всеми модулями. Любое изменение здесь затрагивает всю
систему, поэтому изменения осознанные и отражаются в этом документе.

| Тип | Что это |
|---|---|
| `RawSnapshot` | сырой ответ площадки + метаданные (источник, время) |
| `SourceEvent` | событие глазами одного источника: спорт, лига, участники, время начала |
| `MarketKey` | идентификатор рынка: тип + линия + период (хешируемый) |
| `Quote` | одна котировка: событие + рынок + исход + цена + лимит + время |
| `MatchedEvent` | группа `SourceEvent` разных источников = одно логическое событие |
| `ArbOpportunity` | найденная вилка: набор котировок, маржа, разбивка ставок |

Принципиальные решения:

- **Единица цены — десятичный коэффициент (`decimal_odds`).** Всё приводится к
  нему на границе источника. Вероятность Polymarket `p` → `1/p`. Ничего другого
  внутри системы не ходит.
- **Все времена — UTC, timezone-aware.** Наивных `datetime` в системе нет.
- **Деньги и коэффициенты — `Decimal`, не `float`.**
- **Исходы — перечисления (`HOME` / `DRAW` / `AWAY` / `OVER` / `UNDER`),
  не строки.** Строка с сайта остаётся только в сыром снимке.
- **Модели иммутабельны** (`frozen=True`). Стадия не правит вход, а строит
  новый объект.

### Типы рынков (первая версия)

| `MarketKind` | Исходы | Комментарий |
|---|---|---|
| `MONEYLINE_2WAY` | `HOME`, `AWAY` | спорт без ничьих |
| `ONE_X_TWO` | `HOME`, `DRAW`, `AWAY` | футбол/хоккей, основное время |
| `TOTAL` | `OVER`, `UNDER` | обязательно с `line` |
| `HANDICAP` | `HOME`, `AWAY` | обязательно с `line` |

Рынки сравниваются только при полном совпадении `MarketKey` — включая линию и
период. `TOTAL 2.5` и `TOTAL 3.0` — разные рынки.

## 4. Правила зависимостей

Импорты идут строго «вниз». Нарушение этих правил — повод отклонить правку.

```
Уровень 0 (ничего не импортируют из arbx):
    models.py, odds.py, logging_setup.py

Уровень 1 (только уровень 0):
    config.py, http/*, normalize/*

Уровень 2 (уровни 0–1):
    sources/*, matching/*, arbitrage/*, storage/*, notify/*

Уровень 3 (всё):
    orchestrator/*, cli.py
```

Дополнительно:

- `sources/*` **не импортируют** `matching`, `arbitrage`, `notify`. Адаптер не
  знает, зачем собирают данные.
- Модули одного уровня друг друга не импортируют, за исключением
  `matching` → `storage` (чтение словаря алиасов) через интерфейс репозитория.
- `arbitrage` — чистые функции над `Quote`: ни сети, ни файлов, ни БД.
  Благодаря этому вся математика покрывается тестами тривиально.
- Playwright импортируется лениво внутри `http/browser.py`, чтобы проект
  работал без браузера, пока он не нужен.

## 5. Интерфейс источника

Новая площадка добавляется реализацией одного класса и записью в
`config/sources.yaml`. Больше нигде код не меняется.

```python
class BaseSource(ABC):
    name: str

    @abstractmethod
    def fetch(self, sports: list[str]) -> RawSnapshot: ...

    @abstractmethod
    def parse(self, snapshot: RawSnapshot) -> tuple[list[SourceEvent], list[Quote]]: ...
```

Разделение `fetch` / `parse` принципиально: `parse` — чистая функция от
снимка, поэтому её можно гонять на сохранённых фикстурах в тестах и ноутбуке
без сети.

## 6. Хранение

**Файлы** — для данных:

- `data/raw/<source>/<YYYY-MM-DD>/<timestamp>.json` — ровно то, что вернул
  сайт. Append-only, никогда не перезаписывается.
- `data/normalized/<timestamp>.parquet` — таблица котировок.

**SQLite** (`data/arbx.sqlite`) — для состояния, которое должно пережить
перезапуск:

| Таблица | Назначение |
|---|---|
| `aliases` | подтверждённые соответствия имён команд и лиг |
| `event_links` | подтверждённые связки событий между источниками |
| `pending_links` | кандидаты в серой зоне, ждут ручной проверки |
| `opportunities` | история найденных вилок |
| `alerts_sent` | что уже отправлено, для дедупликации |

## 7. Конфигурация

- `config/settings.yaml` — всё, что хочется менять без правки кода: интервал
  цикла, минимальный профит, окно свежести котировок, пороги сопоставления,
  список включённых источников.
- `config/sources.yaml` — по площадке: базовый URL, задержки, какие виды
  спорта тянуть, нужен ли браузер.
- `.env` — только секреты: токен Telegram, chat id, ключи. В git не попадает;
  перечень переменных — в `.env.example`.

Уже существующие в `.env` ключи (`POLY_PRIVATE_KEY`, `POLY_FUNDER_ADDRESS`)
этому проекту не нужны: торговля не ведётся, публичные данные Polymarket
читаются без авторизации.

## 8. Что берём из `fetching_old`

Старый парсер Polymarket — донор, а не основа. Переносим с переработкой:

| Файл | Что годится |
|---|---|
| `gamma.py` | `build_retry_session`, пагинация событий (keyset и offset) с защитой от зацикливания — переезжает в `http/session.py` и `sources/polymarket/client.py` |
| `parsing.py` | извлечение `outcomePrices` и `clobTokenIds`, сопоставление исходов и токенов — в `sources/polymarket/parse.py` |
| `config.py` | базовые URL Gamma/CLOB — в `config/sources.yaml` |
| `normalization.py` | подход «событие → строки рынков», но схема строки другая |

Не переносим: `clob_client.py` (авторизованная торговля), `fetching.py` и
`historical_fetching.py` (позиции и ордера пользователя), `temp.py`.
